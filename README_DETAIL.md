## 1. 코드 아키텍처 선택 (헥사고날 vs 레이어드)
- **1) 고민한 것**: 외부 인프라 기술(JPA, Kafka, Redis, 외부 SMS/카카오톡 발송 API 등)의 변경에 도메인 비즈니스 룰이 흔들리지 않도록 어떤 코드 아키텍처를 선택해야 하는가?
- **2) 대안**:
  - **A안: 전통적인 레이어드 아키텍처 (Layered)**
    - *장점*: 구조가 단순해 구현 속도가 빠름.
    - *단점*: 비즈니스 로직(Service)이 특정 DB 프레임워크나 외부 전송 모듈에 강하게 결합됨.
  - **B안: 헥사고날 아키텍처 (Ports & Adapters)**
    - *장점*: 핵심 도메인을 순수 자바/코틀린 영역으로 고립시키고 포트와 어댑터를 통해 기술 스택을 유연하게 결합. 테스트 코드 작성이 압도적으로 편리함.
    - *단점*: 인터페이스와 어댑터 구현체 클래스가 늘어나 구현 코드량이 많아짐.
- **3) 결정**: **B안 (헥사고날 아키텍처)**
  - *이유*: 알림 시스템은 외부 메시지 큐, 캐시/분산락, 외부 통신사 API 등 외부 기술 의존도가 극도로 높기 때문에, 기술 변경에 영향받지 않는 도메인 영역 확보와 고신뢰성 테스트 코드 작성이 필수적이므로 채택함.
- **4) 포기한 것**: 초기 폴더 구조의 단순함과 초기 개발 생산성.

## 2. 발송 채널 확장성 패턴 (전략 + 팩토리)
- **1) 고민한 것**: Webhook, Email, SMS, Slack 등 다양한 발송 채널이 지속적으로 추가되거나 요구사항이 변경될 때 분기문(`if-else`)을 제거하고 개방-폐쇄 원칙(OCP)을 어떻게 보장할 것인가?
- **2) 대안**:
  - **A안: 단일 발송 서비스 내 분기 처리**
    - *장점*: 한눈에 로직 흐름을 추적할 수 있어 가시성이 좋음.
    - *단점*: 채널 추가 시마다 기존 발송 서비스 코드를 수정해야 하므로 회귀 버그 발생 확률이 높음.
  - **B안: 전략 패턴(Strategy) + 스프링 빈 팩토리(Factory) 패턴**
    - *장점*: 공통 발송 포트를 인터페이스화하고 채널별 전략 클래스를 각각 생성. 팩토리를 통해 런타임에 빈을 선택하도록 유연하게 확장 가능.
    - *단점*: 채널만큼 파일 개수가 많아짐.
- **3) 결정**: **B안 (전략 패턴 + 팩토리 패턴)**
  - *이유*: 알림 서비스 특성상 새로운 채널 지원 요구는 매우 빈번하므로, 기존 검증된 코드의 변경 없이 신규 발송 클래스만 추가하여 유연하게 확장하기 위해 채택함.
- **4) 포기한 것**: 한 모듈 안에 코드를 모아두고 한눈에 내려다볼 수 있는 코드 가시성.

## 3. 공통 자원 제어 패턴 (AOP 프록시 vs 템플릿/콜백)
- **1) 고민한 것**: 분산 락 획득/해제 및 예외 예방과 같은 공통 관심사(Cross-cutting Concern)를 핵심 비즈니스 로직에서 분리하여 가독성을 높이고 안전하게 자원을 해제하기 위해 어떤 패턴을 써야 하는가?
- **2) 대안**:
  - **A안: 스프링 AOP 프록시 기반 Custom Annotation 패턴**
    - *장점*: 어노테이션 한 줄로 처리가 끝나 비즈니스 서비스 코드가 아주 깨끗함.
    - *단점*: 스프링 프록시 특성상 같은 클래스 내부 호출(Self-Invocation) 시 락이 미작동하는 치명적 맹점이 있고 트랜잭션 종료 시점(커밋)과 락 해제 시점 선후관계를 맞추기 어려움.
  - **B안: 템플릿/콜백 패턴 (LockTemplate + Kotlin Lambda)**
    - *장점*: 프록시의 자가 호출 버그 위험이 원천 제거되며, 락 획득/반납의 물리적인 경계와 커밋 시점을 명시적이고 완전하게 컴파일러 수준에서 안전하게 통제 가능.
    - *단점*: 비즈니스 로직 본문이 람다 블록으로 감싸져 코드 들여쓰기 깊이가 생김.
- **3) 결정**: **B안 (템플릿/콜백 패턴)**
  - *이유*: 분산 락 누수로 인한 장애나 동시성 제어 실패는 치명적이므로, 선언적 마법(AOP) 대신 조금 투박하더라도 흐름을 명확히 추적할 수 있고 예외 안전성이 높은 템플릿/콜백을 채택함.
- **4) 포기한 것**: 인덴트(들여쓰기) 없이 깔끔하게 떨어지는 어노테이션 기반 선언형 코드 가독성.

## 4. 도메인 모델링 방식 (풍부한 도메인 vs 빈약한 도메인)
- **1) 고민한 것**: 알람의 생명주기 상태 전이(Active ➡️ Triggered ➡️ Success/Failed) 규칙을 서비스와 도메인 중 어느 쪽에 응집시켜 도메인 정합성을 보호할 것인가?
- **2) 대안**:
  - **A안: 빈약한 도메인 모델 (Anemic Domain Model)**
    - *장점*: 데이터 매핑과 설계가 직관적이고 빠르게 개발 가능.
    - *단점*: 비즈니스 규칙이 도메인이 아닌 서비스 레이어에 파편화되어 데이터 정합성을 강제하기 어려움.
  - **B안: 풍부한 도메인 모델 (Rich Domain Model / Tactical DDD)**
    - *장점*: 알람(`Alarm`)을 애그리거트 루트로 보고 모든 상태 변경(활성화, 발생, 실패)을 객체 내부 메서드(`alarm.trigger()`, `alarm.fail()`)를 통해서만 캡슐화하여 제어.
    - *단점*: 객체 지향적 캡슐화를 위해 영속성 엔티티와의 변환 레이어와 데이터 매핑 오버헤드가 발생함.
- **3) 결정**: **B안 (풍부한 도메인 모델 - Rich Domain)**
  - *이유*: 알림 시스템의 신뢰성의 핵심은 도메인 객체의 정확한 상태 변화 관리이므로, 비즈니스 지식이 도메인 외부로 유출되는 것을 차단하고 캡슐화를 완수하기 위해 채택함.
- **4) 포기한 것**: DB 테이블 컬럼 정보를 그대로 Getter/Setter로 읽고 쓰는 1:1 방식의 단순함.

## 5. 객체 생성 방식 (기본 생성자 vs 정적 팩토리 메서드)
- **1) 고민한 것**: 도메인 객체가 생성되는 최초 시점부터 잘못된 비즈니스 값(예: 이름 공백 등)으로 불완전하게 초기화되는 것을 어떻게 원천 차단할 것인가?
- **2) 대안**:
  - **A안: 퍼블릭 기본 생성자 직접 호출**
    - *장점*: 코틀린의 기본 문법을 통해 가장 가볍게 인스턴스화 가능.
    - *단점*: 생성 시점의 유효성 검증 로직이 도메인 밖으로 이탈하여 여러 서비스에 흩어질 위험이 있음.
  - **B안: 정적 팩토리 메서드 패턴 (Static Factory Method)**
    - *장점*: 생성 메서드 이름을 통해 생성 의도를 코드로 표현하고, 팩토리 내부 검증 코드(`require(...)`)를 통과해야만 인스턴스를 반환하므로 항상 올바른 도메인만 존재함을 보장.
    - *단점*: 생성자를 private으로 닫고 companion object를 작성하는 보일러플레이트 코드가 증가함.
- **3) 결정**: **B안 (정적 팩토리 메서드 패턴)**
  - *이유*: 도메인 객체는 생성 순간부터 올바른 데이터 정합성을 가져야 하며 불완전한 객체가 생성되는 부작용을 사전에 예방하기 위해 채택함.
- **4) 포기한 것**: 생성자 직접 호출 문법의 간결함.

## 6. 알람 예약/스케줄 사양의 제외 (단발성 즉시 발송 구조 단순화)
- **1) 고민한 것**: 요구사항에 반복 스케줄이나 미래 시각 지연 예약이 없는 상황에서 시스템의 예약 대기열 로직과 데이터 포맷 복잡도를 어떻게 처리할 것인가?
- **2) 대안**:
  - **A안: 예약 시간 필드(`scheduledAt`/`scheduleExpression`) 유지**
    - *장점*: 미래에 예약 발송 기능이 도입될 때 스키마 변경이 없음.
    - *단점*: 현재 쓰이지도 않는 과거/미래 시간 유효성 검증 코드가 남아있어 코드 분석 비용을 높이고, DB 스키마가 지저분해짐.
  - **B안: 예약 스펙 전면 제외 및 즉시 발송 구조로 완전 단순화**
    - *장점*: 스케줄링 대기열 로직과 관련 시간 포맷팅/검증 모듈이 사라져 시스템의 신뢰성과 구조가 고도로 경량화됨.
    - *단점*: 향후 스케줄 기능 도입 시 DB 스키마 마이그레이션이 필요함.
- **3) 결정**: **B안 (예약 스펙 제외 및 즉시 발송 단순화)**
  - *이유*: 불필요한 과잉 엔지니어링(Over-engineering)을 즉시 걷어내고, 현재 알림 즉시 발송 요구사항에만 집중하여 가볍고 견고한 모듈을 제작하기 위해 채택함.
- **4) 포기한 것**: 크론 및 미래 예약 스케줄러로의 확장성.

## 7. 미사용 CRUD API 엔드포인트 전면 제거
- **1) 고민한 것**: 초기 설계에 들어갔던 목록 조회, 수정, 삭제 엔드포인트가 실제 "즉시 발송 및 이력 로깅" 중심의 요구사항에서 불필요하게 코드베이스를 차지하고 있는 문제를 어떻게 처리할 것인가?
- **2) 대안**:
  - **A안: 향후 관리자 도구 등을 고려해 CRUD 엔드포인트를 그대로 유지**
    - *장점*: 추후 조회 및 관리 기능을 재구현할 필요 없음.
    - *단점*: 사용하지 않는 엔드포인트가 노출되어 유지보수 포인트를 늘리고, API 복잡도를 증가시킴.
  - **B안: 단발성 발송 API (`POST /alarms`) 및 발생 API (`POST /alarms/{id}/trigger`)만 남기고 삭제**
    - *장점*: 비즈니스 요구사항에 100% 매핑되는 최소한의 순수한 API 스펙만 유지하여 시스템 품질을 극대화함.
    - *단점*: 이후 개별 조회나 수정이 필요할 경우 신규 구현해야 함.
- **3) 결정**: **B안 (미사용 API 전면 제거)**
  - *이유*: 배포 가능한 고품질 Assignment 코드는 군더더기가 없고 비즈니스 핵심 목적에 완전히 부합해야 하므로, 불필요한 코드를 완전히 격리 및 청소하기 위해 채택함.
- **4) 포기한 것**: 이미 작성되었던 CRUD 코드 아티팩트와 잠재적 조회 API 확장성.

## 8. 락과 트랜잭션의 물리적 경계 분리
- **1) 고민한 것**: 분산 환경에서 다중 요청 시 발생하는 중복 삽입/발송(동시성 레이스 컨디션)을 방지하기 위해 락과 DB 트랜잭션의 상호작용 한계를 어떻게 보장할 것인가?
- **2) 대안**:
  - **A안: 트랜잭션 내부에서 락 제어 (Propagation.REQUIRED 기본값 사용)**
    - *장점*: 프레임워크 설정이 단순함.
    - *단점*: 락이 먼저 반납되고 트랜잭션 커밋은 메서드 리턴 후(나중에) 일어나기 때문에, 그 짧은 틈새에 들어온 중복 요청이 멱등성 필터를 뚫고 중복 발송을 일으킴.
  - **B안: 락 내부에서 `@Transactional(propagation = REQUIRES_NEW)`로 격리 실행**
    - *장점*: 부모 서비스(락 획득) 안에서 자식 헬퍼 서비스(`REQUIRES_NEW` 실행)를 호출해 즉시 물리 커밋을 성공시킨 후 락을 해제하므로, 동시성 레이스 컨디션을 완벽하게 차단.
    - *단점*: 부모 트랜잭션이 있을 때 호출 시 한 스레드가 2개의 커넥션을 점유해 데드락 위험이 있고 자가 호출 프록시 문제를 우회해야 함.
- **3) 결정**: **B안 (REQUIRES_NEW 격리 구조)**
  - *이유*: 락 해제 전 커밋 완료라는 동시성 정합성을 스프링 아키텍처 내부에서 완벽히 달성하여 동시성 레이스 컨디션 버그를 원천 차단하기 위해 채택함.
- **4) 포기한 것**: 단일 서비스 클래스 구조 유지 (동작을 위해 별도의 트랜잭션 헬퍼 빈 분리 적용).

## 9. 커넥션 풀 데드락(Connection Pool Deadlock) 회피 전략
- **1) 고민한 것**: 락 내부에서 `REQUIRES_NEW` 트랜잭션을 실행할 때, 높은 동시 요청 상황에서 스레드들이 커넥션 풀의 연결을 동시 점유하기 위해 대기하다가 시스템 전체가 굳어버리는 데드락 리스크를 어떻게 피할 것인가?
- **2) 대안**:
  - **A안: HikariCP 커넥션 풀 설정을 극도로 늘림**
    - *장점*: 코드가 간단함.
    - *단점*: 서버 스레드 증가 시 DB 커넥션을 너무 많이 생성해 DB CPU/메모리 고갈 위험이 발생함.
  - **B안: 락을 잡는 부모 모듈의 트랜잭션을 전면 해제 (Facade 적용)**
    - *장점*: 부모가 커넥션을 물지 않은 상태에서 락 대기 및 락 획득을 진행하므로, 자식 `REQUIRES_NEW` 실행 시 항상 스레드당 1개의 커넥션만 소모하여 풀 데드락이 완벽히 방지됨.
    - *단점*: 락 획득 계층에 `@Transactional`을 완전히 쓰지 않는 통제를 엄격히 해야 함.
- **3) 결정**: **B안 (부모 트랜잭션 배제 / Facade 패턴화)**
  - *이유*: DB 서버 리소스 낭비 없이 애플리케이션의 트랜잭션 전파 규칙 조절만으로 풀 데드락 안전성을 100% 확보할 수 있기 때문에 채택함.
- **4) 포기한 것**: 부모 락 실행 진입점 계층에서의 선언적 데이터베이스 트랜잭션.

## 10. 동시성 및 중복 제어 엔진 선택 (Redis 분산 락 vs Kafka 큐)
- **1) 고민한 것**: 중복 발송 및 유실 예방의 핵심인 동시성 제어를 위해 API 호출자의 즉각적인 동기적 응답 성공 여부를 우선할 것인가, 메시지를 받는 최종 고객(수신자) 관점의 메시지 유실 및 중복 전송 방지 신뢰성을 우선할 것인가?
- **2) 대안**:
  - **A안: Redis 분산 락 기반 동기 제어**
    - *장점*: API 호출 즉시 발송 완료 성공/실패 여부를 바로 알 수 있음.
    - *단점*: 외부 API 서버 장애로 지연이 길어질 경우 락 획득 대기가 밀려 WAS 스레드 풀이 고갈되고, 인메모리 락 특성상 예기치 못한 크래시 시 유실이 생김.
  - **B안: Kafka 파티션 키 기반 비동기 순차 제어**
    - *장점*: 멱등 키(`requestId`)를 카프카 파티션 키로 삼아 이벤트를 발행하면 동일 요청이 물리적인 단일 파티션 큐로 정렬되어 들어가므로, 분산 락 없이 완벽한 순차 처리와 멱등 소비가 가능. 디스크 영속성(Commit Log) 덕분에 장애 시점에 언제든 재처리(Replay)가 가능해 메시지 유실율이 0%에 수렴함.
    - *단점*: 비동기 처리가 되므로 API 호출자는 `202 Accepted` 접수 응답만 받고 실제 결과는 나중에 확인해야 함.
- **3) 결정**: **B안 (Kafka 파티션 키 기반 비동기 순차 제어)**
  - *이유*: 알림 서비스에서 가장 핵심적인 가치는 **최종 수신 고객이 알림 누락과 중복 발송을 겪지 않는 철저한 신뢰성**입니다. 클라이언트가 API를 호출하고 기다리는 속도보다 메시지 전송의 신뢰성과 장애 내구성이 제품 경쟁력에 압도적으로 중요하므로 카프카 큐를 동시성 제어의 중추로 채택함.
- **4) 포기한 것**: API 호출 시점의 동기식 발송 완료 상태 반환.
