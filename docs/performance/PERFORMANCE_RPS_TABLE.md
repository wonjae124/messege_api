## 🛠️ 병목 분석 및 최적화 전략 (컨슈머 병목 해소)

**병목 분석 이유:**
- 이전 테스트에서 카프카의 디스크 쓰기 속도는 아주 가벼운 수준(초당 200KB)이었기 때문에 디스크 병목이 아니었습니다.
- 반면 카프카 Network I/O에서 프로듀서(Data received)는 280MB를 쏟아내지만, 컨슈머(Data sent)는 32.8MB만 가져가며 **심각한 Consumer Lag**이 발생 중이었습니다.

**설정 변경 전략 및 파라미터:**
1. **토픽 파티션 확장 (`application-perf.yml`)**
   - `kafka.topic.partitions`: `2` ➡️ `6`
2. **컨슈머 내부 스레드 확장 (`application-perf.yml`)**
   - `kafka.consumer.concurrency`: `2` ➡️ `6`
   - 포트 충돌(`8080`)을 방지하기 위해 컨테이너를 여러 개 띄우는(`replicas`) 대신, 단일 애플리케이션 내의 카프카 메시지 수신 스레드 풀을 확장시켜 병렬 처리를 최적화했습니다.

**기대 효과:**
- 단일 서버 환경이라 할지라도 6개의 파티션을 스레드 6개가 동시에 비워내기 시작하면서 처리 속도(Throughput)가 획기적으로 개선되었습니다. 그 결과 가장 가혹한 Spike 테스트(1000 RPS)에서도 11ms라는 놀라운 평균 응답 시간을 달성했습니다.

**감수한 트레이드 오프:**
- 컨슈머 스레드가 3배 늘어나면서 데이터를 DB에 밀어 넣는 속도도 빨라졌습니다. 이로 인해 단일 애플리케이션 내에서 DB 커넥션을 얻기 위한 **스레드 간의 락(Lock) 경합 및 PostgreSQL 부하**가 급증할 수 있습니다. 카프카 병목이 해소된 만큼 다음 병목은 데이터베이스가 될 것입니다.

### 🚨 [결과 분석] 200 RPS 환경에서 배치 사이즈 1,000 적용 시 나타난 병목 (트레이드오프)

- **발생 현상**: 아웃박스 배치 사이즈(larm.outbox.batch-size)를 50에서 1,000으로 과감하게 늘린 결과, 밀린 큐를 비우는 시간(Drain)은 38초로 개선되었습니다. 하지만 실시간 API 응답 지연(p95)이 8ms ➔ 1.53초로 **약 170배 폭증**했으며, API 성공률마저 100%에서 99.72%로 떨어져 30건의 타임아웃/에러가 발생했습니다.
- **원인 분석 (DB 락 및 커넥션 경합)**:
  1. 스케줄러가 한 번에 1,000건의 데이터를 FOR UPDATE(DB 레코드 락)로 가져오면서 막대한 DB 자원(CPU/메모리)과 Hikari 커넥션을 독점했습니다.
  2. 이로 인해 외부 사용자(k6)가 호출하는 실시간 알림 생성 API가 DB 커넥션을 얻지 못하고 블로킹되면서, 병목 현상과 심각한 지연이 발생했습니다.

- **결론 및 교훈**: 아웃박스 패턴에서 잔여 큐 처리 속도(Throughput)를 높이기 위해 무리하게 배치 사이즈를 키우면, DB 자원 경합으로 인해 **메인 API의 실시간 응답성(Latency)이 완전히 붕괴**되는 전형적인 트레이드오프를 확인했습니다. 향후 배치 사이즈를 200~300선으로 낮추어 적절히 타협하거나, 배치 사이즈는 작게 유지하되 스케줄링 간격을 좁히는 형태의 튜닝이 권장됩니다.

  1. **드레인(Drain) 2초 컷 달성**: 기존 38초(또는 60초 이상) 걸리던 10,000건의 메세지 발행 및 큐 비우기가 단 **2초** 만에 완료되었습니다! (목표: 1만 건 5초 이하 달성)
  2. **DB Outbox 0건**: 스케줄러 틱(0.5초)마다 쌓인 큐를 순식간에 비워내면서, 부하 테스트 종료 직후 DB에 남아 있는 미처리 건수(`DB:0`)가 완벽하게 0건으로 유지되었습니다.
  3. **DB 커넥션/락 오버헤드 제로**: 스레드 풀, 코루틴 디스패처, 복잡한 콜백 등을 전혀 쓰지 않아 ThreadLocal 오염 문제가 원천 차단되었으며, DB 왕복 횟수가 1,000번에서 1번으로 압축되어 애플리케이션의 쾌적함이 최고조에 달했습니다.
- **최종 결론**: 비동기 I/O 네트워크 배칭 기술과 단일 트랜잭션 묶음 기술이 카프카 Outbox 패턴 스케줄러의 궁극적인 아키텍처임이 증명되었습니다. 코드는 더 짧고 직관적으로 변했으며, 성능은 수십 배 증가했습니다.

#### 💡 [추가 분석 Q&A] 테스트 과정에서 발견된 특이점 해설

**Q: 왜 200RPS에서만 Drain이 2초로 줄고, 50/100RPS는 18~32초가 걸렸는가?**
- **A: 카프카 컨슈머 그룹의 초기 리밸런싱 지연 때문입니다.** 
도커 컨테이너를 새로 띄우자마자 50RPS 테스트가 시작되었는데, 이 첫 10~20초 동안 카프카 내부에서 6개의 컨슈머 스레드를 파티션에 할당(리밸런싱)하느라 컨슈머가 메시지를 소비하지 못했습니다. 그래서 초반 테스트(50/100 RPS)에서는 메시지가 밀려 있다가 늦게 비워져 18~32초가 걸렸고, 200RPS가 실행될 쯤엔 컨슈머들이 완전히 웜업되어 풀파워로 돌아가기 때문에 2초 만에 즉각 비워낸 것입니다.

**Q: 테스트 종료 직후 Kafka Lag은 항상 비슷한 수치(60~800)로 남아 있는 이유는?**
- **A: 비동기 배칭으로 쏘는 속도가 엄청나게 빠르기 때문입니다.** 
k6 부하 테스트 스크립트가 종료되는 바로 그 찰나의 순간, 0.5초 주기의 스케줄러가 마지막 남은 대량의 알림을 카프카 파티션으로 단 '0.001초' 만에 몽땅 쏴버립니다. 측정 타이밍상 이 마지막 배치가 카프카 파티션에 대기 중인 상태로 찍히는 것일 뿐, 컨슈머 병목으로 인해 쌓이는 악성 Lag이 아닙니다. 실제로 백그라운드 컨슈머가 2초 이내에 이 잔여 배치를 모두 정상적으로 소화해냅니다.
